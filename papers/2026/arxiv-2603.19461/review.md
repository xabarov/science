## Вопрос и основной вклад

Как улучшать не только решателя задач, но и процедуру, которая придумывает его
следующие улучшения? В обычной схеме task agent меняется под управлением фиксированного
редактора. В Hyperagents task agent и meta agent входят в один редактируемый
программный артефакт. Измениться могут и решение задачи, и анализ прошлых попыток,
планирование правок, память, диагностика и число вызовов модели.

DGM-H объединяет это с архивным поиском Darwin Gödel Machine. Архив сохраняет
валидные варианты как возможные stepping stones; поиск не ограничен последним
лидером. Удачная текущая метрика и способность породить удачных потомков — разные
свойства. Улучшение навыка решения, например рецензирования, само по себе не
гарантирует улучшения навыка переписывать программного агента.

## Устройство и граница редактирования

```text
Archive of H=(TaskAgent, MetaAgent, code, results)
    → select parent H
    → its MetaAgent edits task and/or meta implementation
    → compile and evaluate child TaskAgent
    → add valid child + score to archive
    → next parent may come from any archived branch
```

Это программная архитектура, не новая структура нейросети. Foundation models
остаются фиксированными: в non-coding опытах код меняет Claude 4.5 Sonnet,
а task calls используют GPT-4o, Claude 4.5 Sonnet или o4-mini в зависимости от
домена. В robotics внутренняя PPO-политика робота отдельно обучается на каждом
предложенном reward; утверждение о frozen weights относится к foundation models.

Начальная реализация намеренно проста. `TaskAgent.forward(inputs)` вызывает FM
и извлекает поле response. `MetaAgent.forward(repo_path, eval_path, iterations_left)`
открывает tool-enabled сессию с просьбой изменить код репозитория. Сами task_agent.py
и meta_agent.py доступны для изменений; будущий запуск использует изменённый код.

Редактируемы prompts, parsing, tools, память, логирование, retry и control flow.
В основном эксперименте фиксированы данные, evaluator, LLM, внешний iteration
budget и parent-selection rule. Возможность менять parent selection исследована
лишь в отдельном предварительном Appendix E.5. Слово self-referential не означает,
что текущая реализация может менять всю инфраструктуру или критерий собственного
успеха (Appendix A.5).

Parent selection балансирует score и число уже порождённых компилируемых детей.
Для review/math при отборе используется validation score, а не test. Несколько
доменов объединяются средним score; staged evaluation сначала отсеивает явно
неработоспособные варианты, что снижает расходы, но меняет фактический объём
вычислений кандидатов.

## Что проверяли

1. Polyglot coding: изменение кода с executable tests.
2. Paper review: предсказание исторического accept/reject по тексту статьи.
3. Robotics reward design: генерация reward для Go2 в Genesis; обучение ходьбе,
   затем held-out задача максимизации высоты туловища.
4. IMO-GradingBench: присвоение готовому решению оценки из {0,1,6,7} по экспертной
   разметке; используется для переноса метаумений и последующей эволюции.

Paper review — не оценка качества написанной рецензии, истинности научных выводов
или способности находить новые исследования. Robotics — один робот и две цели,
не демонстрация универсального переноса на робототехнику.

## Результаты задачи и сильные baselines

В основных опытах по 5 runs; приводятся медианы и 95% bootstrap CI из 1000
resamples. В статье используется Wilcoxon signed-rank test; реализацию теста и
единицу pairing по логам в этом разборе не проверяли.

| Условия / метрика | DGM-H | Сравнение | Локатор |
| --- | --- | --- | --- |
| Paper review, held-out 100 papers, accuracy; GPT-4o task / Sonnet 4.5 meta, 100 iterations | 0.710 [0.590,0.750] | DGM-custom 0.590 [0.570,0.650]; static AI-Scientist-v2 0.630 | Section 5.1, Figure 2 |
| Go2 held-out height reward design, task score | 0.372 [0.355,0.436] | DGM-custom 0.348 [0.305,0.385]; default reward 0.348 | Section 5.1, Figure 2 |
| Full Polyglot, pass@1, 80 iterations | 0.084→0.267 [0.231,0.280] | Original DGM 0.142→0.307, другой исходный score | Section 5.1 |

DGM-H превосходит некоторые ablations и исходный, неадаптированный под новые домены
DGM. Однако превосходство над вручную адаптированным DGM-custom на review/robotics
не статистически значимо (p>0.05). Full Polyglot включает training subset; это не
полностью независимый test. Нельзя превращать таблицу в общий рейтинг разных моделей.

Особенно важно объяснение нулевого старта: начальные task agents на review/math
не соблюдают требуемый формат. Часть улучшения — освоение интерфейса и parsing,
а не прирост содержательной компетентности LLM. Ноль не означает, что GPT-4o или
o4-mini исходно вообще не умеют рецензировать или оценивать решения.

## Самая содержательная абляция: перенос метаагента

Из source runs на paper review + robotics выбираются hyperagents, породившие
перспективных потомков. Используется descendant-growth criterion с lineage discount,
а не поиск по target test. Затем на новом домене math grading в течение 50 шагов
фиксируется meta agent, а изменяются task agents. Выбор результата — по validation.

`imp@k = test score выбранного по validation лучшего кандидата − test score старта`.

Это выигрыш после бюджета поиска, не zero-shot оценка перенесённой программы и
не вероятность успеха одного изменения. Формальная запись Appendix D.3 через max
Evaluate требует сопоставления с фактическим validation selection, описанным в
Sections 5.2 и D.5; для выводов используем описанный held-out протокол.

| Перенесено | Median test imp@50 | 95% CI |
| --- | ---: | --- |
| Ничего | 0.000 | [0.000,0.130] |
| Только task agent | 0.100 | [0.000,0.560] |
| Только meta agent | 0.620 | [0.550,0.660] |
| Оба | 0.630 | [0.540,0.630] |

Источник: Appendix D.5 Table 4, p. 39; Claude 4.5 Sonnet meta / o4-mini task,
IMO-GradingBench train/val/test по 100, 5 source runs. Это сильнейшая поддержка
центральной идеи: переносимым оказался процесс создания улучшенных решателей.
Task-only результат сильно варьирует, поэтому нельзя утверждать нулевую полезность
любого перенесённого task agent.

## Накопление улучшений и пределы вывода

После 200 iterations на math grading старт с transfer hyperagent даёт test accuracy
0.640 [0.550,0.720], обычный старт — 0.610 [0.510,0.680]. Разница не значима
(p>0.05). Это ограниченная поддержка полезности предыдущего опыта, а не измерение
устойчивого ускорения скорости улучшений.

Отдельный лучший артефакт BetterGrader, полученный от ProofAutoGrader + transfer
meta agent, улучшает результат на полном IMO-GradingBench 0.561→0.601, MAE
0.178→0.175. Это отдельный расширенный набор и выбранный артефакт; его не следует
смешивать с median test-subset 0.640 или результатом 0.670→0.700 на subset.
Нужно также учитывать возможное пересечение полного benchmark с train/validation.

## Стоимость и альтернативные объяснения

Appendix D.2 оценивает 100-итерационный review+robotics run в 83.6M tokens:
33M на modification и 50.6M на evaluation. Оценка не равна всем расходам на пять
повторов и не полностью учитывает обучение robot policies по стоимости GPU.
Одна итерация может содержать разное число вызовов, retries и внутренних процедур.
Сравнение при одинаковом числе iterations не изолирует эффект editable meta agent
от дополнительного inference compute. Авторы прямо оставляют matched-compute
сравнения как продолжение (Appendix F).

Review labels публичны и субъективны; возможны влияние acceptance priors и
запоминание исторических outcomes, чего простой held-out split не исключает.
Proxy gaming остаётся возможным. Улучшение памяти или ведения метрик — конкретные
найденные инженерные процедуры, но их наличие само по себе не доказывает рост
общего интеллекта. При фиксированных данных/evaluator/FM прогресс может насыщаться;
это наблюдается на горизонте сотен iterations. Неограниченное самоускорение —
мотивация, не установленный результат.

## Связь с картотекой и возможная проверка

Наше сравнение: [RRSI](../arxiv-2609.24972/review.md) регулирует траекторию поиска
обвязки, [Harness²](../arxiv-2610.14224/review.md) меняет её на текущей задаче по
контрастам, а Hyperagents делают редактируемым сам редактор. У
[R²Orch](../arxiv-2610.22740/review.md) изменяются обучаемые параметры оркестратора;
[Mid-Harness](../arxiv-2609.39982/review.md) отбирает действия внутри исполнения.
Прямого общего эксперимента между ними в работе нет.

Для нашей картотеки интересен вопрос: улучшает ли редактируемый редактор разборов
верность извлечения фактов при фиксированном полном бюджете? Возможный опыт:
сравнить fixed editor, editable editor и editable editor с RRSI-подобным отбором,
сохраняя закрытый evaluator по числам, единицам, baseline и локаторам. Разделить
новые статьи знакомых направлений и отложенные новые области; учитывать все tokens,
tool calls и время. Опровержение полезности — отсутствие выигрыша относительно
сильного fixed editor при равных затратах или выигрыш только на знакомой рубрике.
Это предложение ассистента; новизна не установлена, интеграция и опыт не запускались.
