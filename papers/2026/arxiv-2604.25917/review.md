# RecursiveMAS и обучение обмена скрытыми состояниями

ID: `arxiv:2604.25917`. RecursiveMAS превращает несколько LLM в рекуррентную
вычислительную систему: промежуточная коммуникация идёт через последовательности
векторов, а обучаемые связи согласуют разные модели. Практический выигрыш —
сократить текстовые сообщения и обучать взаимодействие по ошибке конечного ответа.
Это требует доступа к hidden states и supervised training; обычного chat API мало.

## Архитектура и входы

Обычная схема Planner → Critic → Solver генерирует и повторно кодирует текст
на каждом переходе. Здесь Planner получает текст вопроса и роль, выполняет
несколько autoregressive latent steps и передаёт матрицу H размера m × d₁.
Outer RecursiveLink переводит её в m × d₂ для следующей модели. Critic получает
собственный текстовый контекст вместе с этими input embeddings. Solver затем
возвращает скрытые состояния Planner для следующего раунда. Текстовый ответ
декодируется последним агентом в финальном раунде.

Два модуля из Sections 3.1–3.2:

- Inner: `R_in(h) = h + W2 GELU(W1 h)`. Последний hidden state возвращается
  в input embedding space той же LLM для следующего latent step.
- Outer: `R_out(h) = W3 h + W2 GELU(W1 h)`. Проекция W3 позволяет связать модели
  с разными hidden dimensions; обучается канал передачи, а не общий токенизатор.

Это не один sentence embedding всего рассуждения и не JSON с планом.
Латентная последовательность остаётся вычислительно затратной: каждый шаг
всё ещё требует прохода через LLM. Вариант с инструментами также должен выдавать
явные вызовы Python/Search API и получать их результаты; внешние инструменты
не начинают понимать непрерывные векторы.

Авторы рассматривают четыре структуры: последовательность ролей, смесь
специалистов с Summarizer, пару Expert/Learner и Reflector/Tool-Caller.
Light/Scaled — размеры последовательной системы, а не дополнительные топологии.
[Архитектура проекта](https://recursivemas.github.io/#architecture).

## Что обучается и какие losses

Сначала inner link обучается приближать embedding distribution целевых ответов:
`L_in = 1 - cosine(R_in(H), Emb(y))`. Затем разворачивается цикл всей MAS,
а outer links обучаются по cross-entropy конечного ответа. Base LLM frozen;
во второй стадии фиксируются также inner adapters, но градиент может проходить
через их входы. Frozen weights не равны `no_grad` на всём вычислении.

Обучение использует s1K, m1K, OpenCodeReasoning и ARPO-SFT. Для последовательной
схемы Qwen3.5-397B-A17B переписывает ответы в targets планировщика и критика.
Это дополнительная ролевая супервизия, а не возникновение кооперации без данных.
[Section 4 и Appendix B.3](https://arxiv.org/html/2604.25917v2#S4).

В [released train/model.py](https://github.com/RecursiveMAS/RecursiveMAS/blob/cbfcaab56c9a8f660a9be598750b4ff3cd762056/train/model.py)
inner adapter по умолчанию содержит LayerNorm; для выравнивания предыдущего
hidden state со следующим token embedding предусмотрены cosine и MSE losses.
CLI `train/train_inner.py` по умолчанию задаёт cosine weight=1 и MSE weight=0,
хотя у Python-метода `forward` другое значение MSE по умолчанию. В
[sequential outer training](https://github.com/RecursiveMAS/RecursiveMAS/blob/cbfcaab56c9a8f660a9be598750b4ff3cd762056/train/outer/sequential.py)
используются teacher-forced планы, refined plans и ответы; состояния передаются
между раундами, final-round CE выбран по умолчанию. Это детали реализации сверх
схемы статьи и возможный train/inference gap, не установленная ошибка метода.

## Эксперименты и результаты

Девять benchmarks охватывают математику, научные и медицинские вопросы, код и поиск.
В scaled sequential system Planner — Gemma3-4B-it, Critic — Llama3.2-3B-Instruct,
Solver — Qwen3.5-4B. Сравниваются r=1/2/3 и разные training/inference depths;
есть ablations RecursiveLink и длины latent sequence.

Selected Table 3, r=3, средние результаты авторов:

| Benchmark и метрика, % | Single Full-SFT | Recursive-TextMAS | RecursiveMAS |
| --- | ---: | ---: | ---: |
| AIME2025, pass@10 | 73.3 | 73.3 | 86.7 |
| AIME2026, pass@10 | 76.7 | 73.3 | 86.7 |
| GPQA-Diamond, accuracy | 62.8 | 61.6 | 66.2 |
| LiveCodeBench-v6, code tests | 38.6 | 38.7 | 42.9 |

[Table 3, PDF p. 10](https://arxiv.org/html/2604.25917v2#S5.T3).
AIME pass@10 засчитывает задачу при хотя бы одном успешном ответе из десяти,
поэтому это не вероятность успеха одной попытки. Авторы сообщают пять запусков;
для отдельных ячеек этой таблицы интервалы не приведены.

Заголовочные +8.3% получаются усреднением относительных приростов к лучшему
baseline в каждой из шести колонок Table 3. По тем же округлённым ячейкам
средний абсолютный прирост равен 5.7 п.п. Это наша проверка арифметики, не новый
benchmark. Число +8.3 не является единым выигрышем на всех девяти datasets.

Относительно Recursive-TextMAS авторы сообщают среднее ускорение 1.2×/1.9×/2.4×
и уменьшение token usage 34.6%/65.5%/75.6% при r=1/2/3. Это выходные токены
и измеренное время в конкретных конфигурациях, не равное уменьшение FLOPs.
В Appendix B.3 указаны H100/A100, но точное распределение железа по ячейкам
и единица агрегации Time требуют уточнения для воспроизведения.
[Table 2 и Section 5.4](https://arxiv.org/html/2604.25917v2#S5.T2).

## Ограничения доказательств и воспроизводимости

1. Table 2 и Table 3 содержат несовпадающие ячейки. При r=3 scaled GPQA-D
   Recursive-TextMAS имеет 58.6 в Table 2 и 61.6 в Table 3; AIME2026 RecursiveMAS —
   86.0 и 86.7; LiveCodeBench text baseline — 36.5 и 38.7. Они сохранены с разными
   локаторами и не сведены в одну оценку. Причина в проверенном тексте не установлена.
2. Прямой text-versus-latent baseline полезен, но широкое сравнение не доказывает
   равенство полной вычислительной стоимости всех систем. Single agent использует
   одну модель, RecursiveMAS — несколько; Appendix B.2 для LoopLM называет Ouro-2.6B.
   Подготовка synthetic targets и настройка тоже имеют стоимость.
3. Theorem 4.1 условен. Анализ отдельного Jacobian при assumptions о весах и
   low-entropy outputs не гарантирует стабильности всего произведения Jacobians
   обученных LLM. Нижняя граница spectral norm сама по себе не ограничивает все
   направления градиента. Это наше ограничение интерпретации, не полный proof audit.
4. LatentMAS и другие latent communication работы цитируются как предшественники,
   но LatentMAS не включён в проверенную Table 3. Поэтому «впервые обмен векторами»
   или превосходство над всем этим классом из статьи не следует.
5. Подключение нового backbone требует согласования пространств и обучения links.
   Это не смена модели в обычной API-обвязке. Сами latent sequences не дают
   человеку проверяемого журнала рассуждений.

Официальный README предупреждает, что reference checkpoints служат для знакомства,
а полное воспроизведение требует task-specific training setups.
[Код и инструкции](https://github.com/RecursiveMAS/RecursiveMAS).

## Связь с картотекой и исследовательский смысл

| Работа | Что меняется |
| --- | --- |
| R²Orch | Обучаемые Director/Proposer, граф кооперации и skills |
| Hyperagents / DGM-H | Код task agent и метаагента, который предлагает будущие правки |
| Jeva | Модель выбора/оценки типизированных кандидатов |
| RecursiveMAS | Канал скрытой коммуникации и рекуррентное вычисление при frozen LLM |

Здесь recursion означает повторные вычисления над состоянием задачи.
Это не самоизменение программы и не неограниченное накопление способностей.

Гипотеза ассистента: научить gate выбирать число latent rounds, оставив независимый
аудит ранних остановок. Минимальная проверка — фиксированный r=3, случайная остановка,
confidence gate и тот же gate с аудитом на отложенном домене, при общем бюджете
времени. Измерять качество одной попытки, tail latency и ошибки остановки.
Если экономия пропадает после учёта gate/audit или растёт доля пропущенных ошибок,
полезность гипотезы не подтверждена. Реализации, запусков и поиска новизны нет.
