# Архитектура и развитие

## Решение на старте

| Слой | Сейчас | Зачем |
| --- | --- | --- |
| Первоисточники и разборы | JSON + Markdown, Git | Переносимость, история, ручная проверка |
| Картотека и полнотекстовый поиск | SQLite FTS5 | Локальная работа без сервера |
| Граф | Таблица relations + CLI related | Переходы по основаниям, продолжениям и гипотезам |
| Neo4j | Экспорт CSV + Cypher | Готовность к более сложным графовым запросам |
| Семантический поиск | Пока отсутствует | Потребует выбрать мультиязычную модель и правила чанкинга |
| Автоматический сбор и чтение | Пока отсутствует | Нужны источники, очередь, критерии и бюджет |

Это проектное решение для одной локальной картотеки, не утверждение, что
любая нагрузка на 36 500 полнотекстовых работ уже протестирована.
Число статей само по себе не требует нескольких постоянно работающих БД.

## Проверка масштаба 2026-11-02

На этом компьютере создан и затем удалён временный корпус из **36 500**
синтетических записей с review.md примерно по 3 КБ. Полная индексация заняла
**8,09 с**, размер SQLite — **245,43 МиБ**. Для общего слова, встречающегося во
всех записях, поиск первых 20 результатов: медиана **91,65 мс**, максимум
**92,77 мс** по 12 последовательным запросам.

Это короткие однотипные заметки и повторяющиеся запросы на локальном диске,
не полные статьи, не холодный кэш и не проверка нескольких одновременных пользователей.
Результат подтверждает работоспособность стартового индекса на планируемом числе
карточек; производительность реального корпуса нужно измерять отдельно.
Машиночитаемый протокол локально: exports/benchmark.json (производный файл вне Git).

## Устройство индекса

`documents` хранит карточки; `aliases` объединяет идентификаторы;
`concepts` связывает записи с нормализованными темами/методами/датасетами;
`relations` хранит ориентированные рёбра с provenance; `search_index` — FTS5.
Собственные заметки индексируются наравне со статьями. Внешние цели связи
могут не иметь карточки и явно показываются как неразобранные.

`index` сначала проверяет все файлы, затем целиком обновляет производные таблицы
в одной транзакции. Читатели видят согласованный снимок. SQLite работает в WAL.
Повторный `index` не накапливает дубликаты; удалённые записи исчезают из индекса.
Ошибочная карточка не заменяет предыдущий успешный индекс.

На первом этапе это полная пересборка. Её время зависит от числа и размера
заметок. Поиск не пересобирает индекс автоматически. На реальном корпусе нужно
измерить время индексации, p95 поиска, объём и время восстановления. Если полная
индексация перестанет укладываться в рабочую сессию, добавить хеши по документам
и инкрементальное обновление, сохранив атомарность пачки.

FTS использует Unicode61 и BM25. Русский текст индексируется, но без русской
лемматизации. Для морфологии сейчас использовать префиксы. Синонимы контролируемых
понятий добавляются в поисковый текст, а не угадываются моделью.
Техническая основа: [SQLite FTS5](https://www.sqlite.org/fts5.html).

## Когда подключать следующий слой

1. **Полные тексты.** Сохранять HTML/PDF, SHA-256, URL, версию и дату загрузки в
   манифесте вложений. Делить текст по разделам и сохранять locator/page.
   Вложения хранить отдельно; автоматическое скачивание пока не реализовано.
2. **Гибридный поиск.** BM25 + мультиязычные embeddings + reranking.
   Каждый фрагмент должен вести к конкретной версии источника. Хранить имя/версию
   embedding-модели, размерность, хеш текста и дату. Сначала сформировать набор
   реальных запросов и проверить recall и качество ссылок.
3. **Neo4j.** Полезен для длинных цепочек и исследования подграфов: «какие идеи
   опираются на неподтверждённое предположение?» Подключать как производную
   проекцию; не вести параллельное ручное редактирование файлов и графа.
4. **Сбор.** Очередь задач с состояниями discovered/fetched/triaged/reviewed,
   повторами, дедупликацией и журналом происхождения. Одно упоминание не должно
   создавать несколько карточек. Планировать отдельно от чтения.
5. **Совместная работа.** Если появятся независимые писатели и серверный UI,
   рассмотреть PostgreSQL и объектное хранилище. Мигрировать по измеренной
   потребности; сохранять ID и происхождение утверждений.

## Данные и резервные копии

Git хранит исходники, но локальный Git сам по себе не резервная копия компьютера.
Рекомендуется регулярная копия `science/` на другой носитель; подключение remote
и облака выполняется по отдельному запросу. `attachments/` исключён из Git:
вложения нужно включать в самостоятельное резервирование.

После потери `data/` достаточно `python3 science.py index`.
При резервировании работающего SQLite использовать SQLite backup API либо
копировать исходники и пересобрать индекс; один файл БД без WAL не является
надёжным снимком живой базы. Не хранить единственные заметки внутри БД.

## Нерешённые задачи

- Нет поиска по embeddings, русской морфологии, OCR и автоматического импорта PDF.
- Нет фонового расписания, сетевого сервера и интерфейса браузера.
- JSON validation проверяет форму, не научное качество; экспертная оценка остаётся необходимой.
- Нет надёжной оценки новизны идеи по одной картотеке: нужен внешний поиск.
- Авторы пока сохраняются строками; ORCID и разрешение однофамильцев — следующий уровень.
- Граф утверждений сейчас представлен claims внутри карточки и связями документов;
  адресные рёбра claim-to-claim нужно добавить, когда появятся такие запросы.
